When the user asks me to choose between options, or says they do not know what is best, for a real choice they will act on (not code reviews, factual lookups or debugging), invoke the `decide` skill.

Run every test suite, build or other memory-heavy command under a cap, one at a time per agent (all capped runs share the 14G orchestrate.slice budget: count 6G per heavy run and 3G per other, so at most about 4 light or 2 heavy at once): `systemd-run --user --scope --quiet --slice=orchestrate.slice -p MemoryMax=6G -p MemorySwapMax=1G -- bash -c 'cd <repo> && <command>'`. Uncapped runs can push a 32 GB machine to swap and risk systemd-oomd killing every session in the terminal. Exit 137 or "Killed" means the command hit the cap: never rerun it uncapped; if other capped runs were live, rerun it alone once, and only a kill when alone is a memory leak to report.

Subagents: the main session runs Opus at high effort; every subagent runs on Sonnet, never Haiku. Use superpowers skills (if installed) for the process (brainstorming, writing-plans, TDD, debugging, verification, finishing a branch), but where one would dispatch subagents, use this setup instead:
- Executing a plan or 2+ independent code changes (superpowers:subagent-driven-development, superpowers:dispatching-parallel-agents, the writing-plans handoff): the `orchestrate` skill with the `worker`, `tester` and `reviewer` agents. This applies under superpowers:test-driven-development too. Exception, as in that skill's step 1.4: a fix you have already designed, with its failing test written, under about 10 lines in a file you have read, you make yourself, and one reviewer checks all such fixes together.
- A code review superpowers asks for (requesting-code-review, executing-plans and final reviews): the `reviewer` agent, using superpowers' review template as the brief, prefixed with `Repo: <absolute repo path>` and the commit range; when the work is uncommitted, give a pre-change snapshot dir or a `diff -ruN` file instead. The reviewer replies in its own VERDICT format.
- Before pushing to a remote that is or will be public, publishing a page, or posting generated content: run the `security` agent over whatever leaves the machine (leaks, private names from ~/.claude/security/private-terms.txt, secure coding). A FAIL blocks it.
- Live state of the user's own hosts and services (configs, versions, logs, API shapes): the `inspector` agent (read-only, existing SSH connections only, read-only MCP), instead of long probing in the main session.
- End-to-end checks of finished work (a page in a headless browser, a CLI's real output, one capped live call): the `verifier` agent.
- Research that means reading external docs or the web (library/API behaviour, versions, protocols, known failure modes): the `researcher` agent, so the pages stay out of the main context; its sourced report counts as the research step.
- Any other subagent (builder checks, skill test runs, Explore, Plan, general-purpose, web-fetch) also runs on Sonnet: settings.json forces it, so do not pass `model`.
A fork keeps the main model, so use a fork when a second opinion needs Opus. Subagents treat their brief as both the go-ahead and the research for their task. If your own CLAUDE.md has rules such as "list the steps and wait for a go" or "research before working", they apply to the main session, not to subagents.
